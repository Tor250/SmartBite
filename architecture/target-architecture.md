# Целевая архитектура SmartBite

Целевая архитектура показывает, как SmartBite может развиваться от подбора рецептов к профилю, книге рецептов и дополнительным сервисам. Новые возможности будут прорабатываться по мере развития продукта.

## Контекст системы

```mermaid
flowchart LR
    user([Пользователь])
    web[Веб-клиент]
    tg[Telegram-клиент]
    app[SmartBite]
    model[Сервис генерации]
    mail[Почтовый сервис]
    food[База пищевой ценности]

    user --> web
    user -.-> tg
    web -->|HTTPS / JSON| app
    tg -.->|HTTPS / JSON| app
    app -->|запрос рецепта| model
    app -.->|письмо для входа| mail
    app -.->|данные для КБЖУ| food
```

Сплошными линиями показан основной веб-сценарий и генерация рецепта. Пунктиром обозначены Telegram-клиент и внешние источники для будущих функций. Подключение этих возможностей будет прорабатываться отдельно.

## Контейнеры и внешние зависимости

```mermaid
flowchart TB
    subgraph clients[Клиенты]
        browser[Веб-приложение]
        telegram[Telegram-бот]
    end

    subgraph smartbite[SmartBite: один модульный монолит]
        api[REST API]
        usecases[Прикладные сценарии]
        modules[Модули продукта]
        adapters[Адаптеры внешних сервисов]
        api --> usecases
        usecases --> modules
        modules --> adapters
    end

    db[(PostgreSQL)]
    recipe_ai[Поставщик генерации]
    email[Почтовый сервис]
    nutrition[Источник состава продуктов]

    browser -->|HTTPS / JSON| api
    telegram -.->|HTTPS / JSON| api
    modules -->|чтение и запись| db
    adapters -->|HTTPS / JSON| recipe_ai
    adapters -.->|HTTPS| email
    adapters -.->|HTTPS / данные| nutrition
```

Веб-клиент и Telegram-бот используют одни прикладные сценарии через REST API. Правила рецептов, работа с профилем и сохранение находятся в backend, а не дублируются в интерфейсах. Все модули backend работают в одном процессе.

## Основные модули backend

```mermaid
flowchart LR
    api[REST API] --> auth[Учётная запись и профиль]
    api --> recipe[Подбор и изменение рецепта]
    api --> library[Книга и обмен рецептами]
    api --> feedback[Оценки и отзывы]

    recipe --> safety[Проверка результата]
    recipe --> generation[Порт генерации]
    generation --> model[Адаптер модели]
    auth --> email[Адаптер почты]

    auth --> data[Репозитории данных]
    recipe --> data
    library --> data
    feedback --> data
    safety --> data
    data --> db[(PostgreSQL)]

    feedback --> events[События аналитики]
    events --> data
```

SmartBite проверяет рецепт до выдачи пользователю. Прикладной сценарий обращается к генератору через отдельный интерфейс, поэтому смена поставщика модели не требует менять правила продукта и формат ответа API. Исключения пользователя проверяются на сервере; ответ внешней модели сам по себе не подтверждает безопасность блюда.

## Потоки ключевых операций

### Подбор рецепта

```mermaid
sequenceDiagram
    actor U as Пользователь
    participant C as Клиент
    participant A as REST API
    participant R as Сценарий рецепта
    participant G as Адаптер генерации
    participant M as Внешняя модель
    participant S as Проверка результата

    U->>C: Ввод продуктов и пожеланий
    C->>A: Запрос рецепта
    A->>R: Проверенные поля запроса
    R->>G: Запрос черновика
    G->>M: HTTPS / JSON
    M-->>G: JSON-ответ
    G-->>R: Разобранный рецепт
    R->>S: Проверка структуры и состава
    S-->>R: Результат проверки
    R-->>A: Рецепт или понятная ошибка
    A-->>C: Ответ API
    C-->>U: Результат
```

### Целевой вход по одноразовому коду

В целевом варианте пользователь подтверждает адрес электронной почты одноразовым кодом.

```mermaid
flowchart LR
    email[Ввод адреса почты] --> issue[Создание одноразового кода]
    issue --> mail[Почтовый сервис]
    mail --> enter[Ввод кода из письма]
    enter --> verify[Проверка кода]
    verify --> session[Создание сессии]
    issue --> db[(Хэш кода и срок действия)]
    session --> db
```

Пользователь вводит адрес почты, получает одноразовый код и подтверждает его в приложении. SmartBite проверяет код и срок его действия, затем создаёт сессию. В базе хранятся хэш кода и данные сессии; пароль не требуется.

## Развитие по Iterative Enhancement

Целевая архитектура может опережать реализацию. В Iterative Enhancement работа начинается с полезного подмножества продукта, а затем повторяются проектирование, реализация и анализ. По результатам каждого цикла можно уточнять требования и архитектуру, расширять или перерабатывать уже работающие части.

```mermaid
flowchart LR
    i1["1 · Базовый подбор<br/>проверен"]
    i2["2 · Аккаунт и профиль<br/>сквозная проверка"]
    i3["3 · Подбор по пожеланиям<br/>сквозная проверка"]
    i4["4 · Книга, отзывы, обмен<br/>сквозная проверка"]
    i5["5 · КБЖУ и расширенные проверки<br/>дальнейшее развитие"]

    i1 --> i2 --> i3 --> i4 --> i5
```

Базовый подбор проверен в демонстрации. Для сценариев следующих итераций предстоит проверить работу целиком — от ввода данных до результата и сохранения.

## Архитектурные решения и ограничения

- **Backend:** модульный монолит с одним процессом и REST API. Telegram и другие клиенты подключаются как новые интерфейсы.
- **Хранение:** PostgreSQL для постоянных аккаунтов, профилей, рецептов и обратной связи. SQLite подходит для локального запуска и разработки.
- **Генерация:** серверный адаптер внешней модели; ключи не передаются браузеру. Ответ проверяется по контракту и правилам SmartBite.
- **Безопасность рецептов:** проверки названий и состава снижают риск неподходящего результата, но не подтверждают скрытые ингредиенты и перекрёстное загрязнение.
- **Почта:** отдельный адаптер отправляет одноразовый код или ссылку; проверку выполняет модуль учётной записи SmartBite.
- **КБЖУ:** будущий модуль использует источник пищевого состава и расчёт порции; модель генерации не является источником точных пищевых значений.
- **Аналитика:** события без текста запросов и секретов; состав набора событий и срок хранения задаются отдельно.
- **Обмен рецептами:** публичная ссылка содержит случайный токен; доступ к личному профилю и книге по ссылке не предоставляется.
