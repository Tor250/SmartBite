# SmartBite — черновая архитектура продукта

## Решение

Целевой продукт строится как веб-приложение из трёх частей: интерфейс, сервер приложения и база данных. Первый MVP использует только основной сценарий генерации из имеющихся продуктов и проверку явных исключений; остальные части архитектуры нужны для последующего развития. Интерфейс не обращается к генератору рецептов напрямую: запросы и ключи внешнего сервиса проходят только через сервер.

- Интерфейс: React / Next.js.
- Сервер: FastAPI.
- Хранение: PostgreSQL.
- Генерация: интерфейс `RecipeJsonClient` и адаптеры внешних моделей. Gemini используется как базовая настройка, модель задаётся через конфигурацию; Qwen доступен для сравнительной проверки. Ответ принимается по общему JSON-контракту и разбирается сервером.
- Прикладной сценарий: общий код генерации и проверки, не зависящий от интерфейса. Сейчас его вызывают HTTP API и консольный адаптер; позднее к нему можно подключить Telegram-бота.

Стиль, выбор БД и способ интеграции обоснованы в `architecture/ADR-001-modular-monolith.md`, `architecture/ADR-002-postgresql.md` и `architecture/ADR-003-rest-and-sync-generation.md`.

## Основные части

1. **Запрос MVP** — пользователь указывает продукты, которые есть дома, и пищевые исключения для этого запроса. Позже добавляется режим генерации по пожеланиям к блюду: если пользователь укажет продукты дома, система покажет, какие ингредиенты потребуется докупить.
2. **Генератор** — возвращает название рецепта, ингредиенты с количеством, список шагов и необязательное время для всего рецепта и каждого шага. Все ингредиенты должны входить в список пользователя.
3. **Проверка результата** — сервер сверяет названия ингредиентов с явными исключениями и словарём поддерживаемых синонимов. Совпадение, неоднозначное название, некорректный ответ или сбой проверки блокируют показ рецепта.
4. **Профиль и книга рецептов** — последующее расширение: учётная запись, сохранение предпочтений и исключений, хранение, повторное открытие и удаление рецептов.
5. **Обратная связь и метрики** — последующее расширение: оценка рецепта и обезличенные события для расчёта D7.

## Данные

В первом MVP запрос содержит список продуктов и исключений; результат генерации показывается после успешной проверки и не требует постоянного профиля или книги рецептов.

Для дальнейшего развития могут храниться:

- **Пользователь и профиль:** данные входа, предпочтения и исключения.
- **Рецепт:** владелец, ингредиенты, количества, шаги, дата создания и результат проверки.
- **Оценка:** пользователь, рецепт, отметка "подходит" / "не подходит".
- **Событие использования:** внутренний идентификатор пользователя, тип события, время. Текст запроса и состав блюда в события не включаются; связанные данные удаляются вместе с профилем.

## Обработка запроса

1. Сервер проверяет, что список продуктов заполнен, и принимает список явных исключений.
2. Передаёт генератору список продуктов через адаптер. Исключения остаются на сервере и проверяются после генерации: генератор не может отменить или обойти это правило.
3. Разбирает JSON ответа по общей схеме: название, ингредиенты с количеством, шаги с необязательной длительностью и необязательное общее время. Некорректные типы и значения приводят к отказу от результата.
4. Сверяет каждый ингредиент с исключениями и словарём синонимов; дополнительно блокирует явное упоминание исключения в шагах приготовления.
5. Показывает рецепт только после успешной проверки. Если генератор или проверка недоступны, сообщает об ошибке и оставляет введённые данные в форме.

Словарь ингредиентов ограничен. В интерфейсе нужно прямо объяснить, что проверка названий не выявляет скрытые компоненты и следы перекрёстного загрязнения и не заменяет медицинскую рекомендацию. Нельзя сообщать пользователю, что продукт гарантированно безопасен.

## Граница MVP

Первый MVP включает один сценарий — запрос рецепта из имеющихся продуктов; ввод пищевых исключений; структурированный рецепт без обязательного времени приготовления; проверку результата до показа; понятную обработку пустого запроса, сбоя генератора, совпадения и неоднозначности. Регистрация, постоянный профиль, генерация по пожеланиям к блюду с показом ингредиентов для покупки, книга рецептов, встроенная оценка, события D7, КБЖУ и оплата не являются обязательными для этого сценария.

При наличии `GEMINI_API_KEY` сервер использует настроенный адаптер Gemini; без ключа приложение запускает демонстрационный генератор. Путь к другому адаптеру задаётся конфигурацией. Оба режима используют общий контракт результата; демонстрационный режим не обращается к внешней модели.

## Направление развития после MVP

Конечная версия может дополнить базовый подбор рецептов следующими возможностями:

- расчёт калорийности и белков, жиров и углеводов (КБЖУ) с указанием исходной базы, порции и точности оценки;
- многоэтапная проверка рецепта: детерминированные правила и матрица несовместимости, проверка полноты состава и, как дополнительный слой, независимая модель ИИ;
- расширенный профиль аллергий, пищевых ограничений и диет;
- справочник сочетаний продуктов и медицинских состояний: для каждого утверждения указывать источник, дату или версию и область применимости.

Справочник не должен сам ставить диагноз или делать универсальный вывод "при этом диагнозе продукт запрещён" без подтверждённого источника. Если рекомендация зависит от индивидуального состояния или источник не найден, сервис показывает ограничение и предлагает обсудить вопрос со специалистом. Все слои проверки должны выдавать раздельные результаты; согласие нескольких моделей само по себе не считается медицинским подтверждением.

Эти направления выходят за границы MVP. Архитектуру данных и проверки стоит строить так, чтобы позже можно было добавлять источники и новые проверяющие компоненты, не подменяя ими базовую проверку ингредиентов. Все функции остаются бесплатными в пределах базовых лимитов; подписка может увеличить лимит хранения рецептов в книге, не закрывая остальные функции.

## Условия работы демонстрационной версии

1. Небольшой начальный словарь ингредиентов и синонимов, которые проверяет MVP; неизвестные или неоднозначные названия блокируются.
2. Ключ и настройки внешнего генератора хранятся только на сервере; сетевой тайм-аут задаётся в адаптере. Исключения проверяются на сервере и не передаются внешней модели.
3. Запросы и результаты MVP не сохраняются в БД. Журнал хранит только идентификатор запроса, маршрут, код ответа и длительность; срок хранения журналов нужно определить перед публичным пилотом.
